ВВЕДЕНИЕ

Актуальность темы. На сегодняшний день проблемы, связанные с поддержанием здорового образа жизни, приобретают особую значимость. Согласно данным Всемирной организации здравоохранения, хронические неинфекционные заболевания — сердечно-сосудистые, диабет, ожирение — являются причиной более 70 % всех смертей в мире. Значительная часть этих заболеваний связана с недостаточной физической активностью, несбалансированным питанием и отсутствием регулярного самоконтроля ключевых показателей здоровья. В этих условиях мобильные приложения для мониторинга здоровья становятся доступным инструментом, позволяющим каждому человеку самостоятельно отслеживать артериальное давление, массу тела, активность и самочувствие, формируя осознанное отношение к своему здоровью.

Несмотря на то, что на рынке присутствуют такие решения, как Samsung Health, Google Fit и Apple Health, большинство из них сфокусированы на одной экосистеме, требуют постоянного подключения к облачным сервисам и не обеспечивают достаточного уровня конфиденциальности медицинских данных. Существует необходимость в приложении, реализующем принцип privacy-first — когда все данные хранятся исключительно на устройстве пользователя, а обработка ведётся локально. Это обуславливает актуальность темы настоящей дипломной работы.

Цель дипломной работы — разработка нативного мобильного приложения для операционной системы Android, предназначенного для комплексного мониторинга показателей здоровья и физической активности пользователя с обеспечением полной конфиденциальности медицинских данных.

Задачи исследования:
1) изучить существующие подходы к разработке мобильных приложений для мониторинга здоровья и провести анализ рынка;
2) провести сравнительный анализ современных технологий для Android-разработки (Kotlin/Jetpack Compose, Flutter, React Native) и обосновать выбор инструментов;
3) сформировать функциональные и нефункциональные требования к приложению;
4) спроектировать архитектуру приложения на основе принципов Clean Architecture с разделением на модули domain, data и presentation;
5) спроектировать схему локальной базы данных и разработать слой доступа к данным на основе Room;
6) реализовать бизнес-логику (use case-классы) для всех функциональных возможностей приложения;
7) реализовать пользовательский интерфейс с использованием Jetpack Compose и Material Design 3;
8) обеспечить механизмы шифрования конфиденциальных данных (фотографий) с использованием Google Tink и Android Keystore;
9) реализовать интеграцию с Android Health Connect для получения данных о физической активности;
10) реализовать генерацию PDF-отчётов на базе нативного Android API;
11) провести тестирование приложения и выполнить анализ результатов.

Объект исследования — процесс разработки мобильных приложений для мониторинга показателей здоровья и физической активности на платформе Android.

Предмет исследования — методы и технологии проектирования и реализации Android-приложения на основе современного стека Kotlin / Jetpack Compose / Room / Koin с интеграцией Android Health Connect и обеспечением локального хранения медицинских данных.

Практическая значимость работы заключается в создании готового к использованию мобильного продукта, который реализует концепцию privacy-first, не требует регистрации и работы в сети, а также соответствует современным стандартам Android-разработки (Material Design 3, Clean Architecture, Jetpack Compose).

Структура работы. Дипломная работа состоит из введения, трёх глав, заключения и списка использованной литературы. В первой главе проводится теоретический анализ современных технологий мобильной разработки и рынка приложений для здоровья. Во второй главе рассматривается проектирование архитектуры, базы данных, бизнес-логики и пользовательского интерфейса приложения. В третьей главе описывается практическая реализация — представлены все экраны приложения, генерация PDF-отчётов и интеграция с Health Connect. В заключении приводятся основные результаты работы и перспективы её развития.

1.1 Изучение современных технологий для разработки мобильных приложений

Разработка мобильных приложений на сегодняшний день представляет собой одну из наиболее динамично развивающихся областей программной инженерии. Согласно данным Statista, в 2025 году общее число пользователей смартфонов в мире превысило 6,9 миллиарда человек, а доля пользователей мобильных приложений для здоровья составила более 45 % от общего числа активных пользователей смартфонов.

Существуют несколько основных подходов к разработке мобильных приложений, каждый из которых имеет свои особенности и область применения:

— Нативная разработка предполагает использование языков и инструментов, официально поддерживаемых производителем платформы: Kotlin и Java для Android, Swift и Objective-C для iOS. Такой подход обеспечивает максимальную производительность, полный доступ ко всем возможностям платформы и наилучший пользовательский опыт, однако требует разработки двух отдельных кодовых баз для двух платформ.

— Кроссплатформенная разработка позволяет создавать приложения для нескольких платформ из единой кодовой базы. Наиболее популярными решениями являются Flutter (Google, язык Dart) и React Native (Meta, язык JavaScript/TypeScript). Этот подход существенно сокращает время разработки, но может уступать нативным решениям по производительности и по степени интеграции с платформенными API.

— Гибридная разработка основана на использовании веб-технологий (HTML, CSS, JavaScript), упакованных в контейнер нативного приложения (Cordova, Ionic). Подход подходит для простых информационных приложений, но плохо работает для приложений, активно использующих сенсоры устройства.

Для разработки мобильного приложения в рамках настоящей дипломной работы был выбран нативный подход с использованием языка Kotlin и декларативного UI-фреймворка Jetpack Compose. Такой выбор обусловлен необходимостью тесной интеграции с платформенными API (Health Connect, датчики шагов, камера), высокими требованиями к производительности и безопасности обработки медицинских данных.

Kotlin — это статически типизированный язык программирования, разработанный компанией JetBrains и официально поддерживаемый Google в качестве основного языка для Android-разработки начиная с 2017 года. Ключевые преимущества Kotlin:
— полная совместимость с Java;
— лаконичный и выразительный синтаксис;
— встроенная поддержка null-безопасности на уровне системы типов;
— поддержка корутин (coroutines) для асинхронного программирования;
— функциональные возможности: лямбда-выражения, функции высшего порядка, расширения классов.

Jetpack Compose — это современный декларативный UI-фреймворк для Android, полностью заменивший устаревшую систему XML-разметок. Compose строит интерфейс путём композиции функций с аннотацией @Composable. Состояние интерфейса управляется реактивно: при изменении состояния система автоматически перерисовывает только те части UI, которые зависят от изменённого состояния.

1.3 Анализ рынка мобильных приложений для мониторинга здоровья

Рынок мобильных приложений для здоровья и фитнеса (mHealth) является одним из наиболее быстрорастущих сегментов мобильной индустрии. По данным аналитического агентства Statista, объём мирового рынка mHealth в 2024 году составил около 72 миллиардов долларов США, а к 2030 году, по прогнозам, превысит 200 миллиардов долларов. Количество пользователей приложений для здоровья в 2025 году превысило 1,5 миллиарда человек.

Основные категории приложений для здоровья:
— трекеры активности (шагов, калорий, тренировок): Google Fit, Samsung Health, Strava;
— приложения для мониторинга хронических заболеваний (давление, глюкоза): MyTherapy, One Drop;
— приложения для психического здоровья и медитации: Calm, Headspace;
— комплексные платформы здоровья: Apple Health, Samsung Health;
— приложения для питания: MyFitnessPal, FatSecret.

Ключевой тенденцией рынка последних лет является рост внимания к конфиденциальности медицинских данных. Согласно опросу Pew Research Center (2024 г.), 78 % пользователей выражают обеспокоенность тем, как приложения для здоровья обрабатывают их персональные медицинские данные, и 62 % пользователей готовы предпочесть приложение с локальным хранением данных даже при ограничении функциональности.

Анализ рынка Казахстана и стран СНГ показывает, что доля пользователей мобильных приложений для здоровья в Республике Казахстан в 2025 году составила 34 % от общего числа владельцев смартфонов, что соответствует среднемировому показателю. По данным Бюро национальной статистики РК, уровень распространённости гипертонии среди взрослого населения Казахстана составляет около 33 %, сахарного диабета — около 9 %, избыточной массы тела — 55 %. Эти показатели значительно выше среднемировых и подчёркивают потребность в массовых инструментах самоконтроля здоровья.

Особенностью рынка Казахстана является преобладание Android-устройств (около 86 % по данным StatCounter на 2025 год), что делает разработку нативного Android-приложения приоритетным подходом для охвата максимально широкой аудитории. При этом значительная часть пользователей использует устройства среднего и бюджетного ценового сегмента с ограниченными вычислительными ресурсами, что требует от приложения высокой производительности и малого размера установочного пакета.

Распространённость носимых устройств (фитнес-браслетов Xiaomi Mi Band, Samsung Galaxy Watch, Apple Watch) в Казахстане в 2025 году достигла 22 %. Это обуславливает целесообразность интеграции с экосистемой Android Health Connect, которая объединяет данные от всех поддерживаемых носимых устройств в едином API.

Рынок mHealth-приложений сегментирован по следующим категориям пользователей:
— пациенты с хроническими заболеваниями (гипертония, диабет), которым необходим регулярный самоконтроль показателей;
— люди, занимающиеся фитнесом и работающие над снижением массы тела;
— пожилые пользователи, которым важна простота интерфейса и крупный шрифт;
— спортсмены и любители активного образа жизни;
— пользователи, заботящиеся о конфиденциальности медицинских данных и предпочитающие локальные решения.

Для разрабатываемого приложения целевыми сегментами являются первые две и последняя категории, поскольку именно они в наибольшей степени нуждаются в функциональности, сочетающей мониторинг показателей и гарантии конфиденциальности.


1.4 Обзор существующих решений и анализ конкурентов

Для формирования функциональных требований к разрабатываемому приложению был проведён анализ трёх наиболее популярных решений, представленных на рынке: Samsung Health, Google Fit и Apple Health.

Samsung Health — комплексное приложение для мониторинга здоровья, предустановленное на устройствах Samsung. Поддерживает отслеживание шагов, веса, артериального давления, сердечного ритма, сна и тренировок. Основные особенности: глубокая интеграция с носимыми устройствами Samsung, социальная функция «Совместные цели», встроенные тренировки. Основные недостатки: требует учётной записи Samsung, отправляет данные в облако Samsung Cloud, ограниченная кастомизация.

Google Fit — приложение для мониторинга активности от Google. Поддерживает трекинг шагов, тренировок, интеграцию с устройствами Wear OS, сердечного ритма. Основные особенности: кроссплатформенность (Android, iOS, web), интеграция с Health Connect. Основные недостатки: фокус только на активности, отсутствие мониторинга давления и самочувствия, обязательная привязка к Google-аккаунту.

Apple Health — встроенное приложение экосистемы iOS. Предоставляет наиболее полный набор функций: шаги, вес, давление, глюкоза, сон, менструальный цикл, медицинские записи. Основные особенности: концепция медицинской карты, сквозное шифрование данных, интеграция с Apple Watch. Основной недостаток: недоступно на платформе Android.

1.7 Обзор и сравнение архитектурных подходов в Android-разработке

Для создания масштабируемых и поддерживаемых мобильных приложений используются различные архитектурные шаблоны, каждый из которых имеет свои сильные и слабые стороны:

— MVC (Model-View-Controller) — классический шаблон, при котором модель отвечает за данные, представление за UI, а контроллер связывает их. В Android-разработке MVC использовался в ранних приложениях, однако страдает от чрезмерной связности Activity с моделью и представлением.

— MVP (Model-View-Presenter) — развитие MVC, в котором презентер становится посредником между моделью и представлением. Упрощает тестирование, однако требует явного управления жизненным циклом презентеров.

— MVVM (Model-View-ViewModel) — шаблон, в котором ViewModel экспонирует состояние в виде наблюдаемых объектов. Официально рекомендован Google для Android и естественно сочетается с Jetpack-библиотеками (ViewModel, LiveData, StateFlow).

— Clean Architecture — архитектурный подход, предложенный Робертом Мартином, разделяющий приложение на слои: бизнес-логика (domain), работа с данными (data) и пользовательский интерфейс (presentation). Зависимости направлены от внешних слоёв к внутренним, что обеспечивает независимость бизнес-логики от конкретных технологий.

В рамках настоящей работы применяется Clean Architecture с разделением проекта на три Gradle-модуля: `domain`, `data`, `app` (presentation). Такой подход обеспечивает высокую модульность, лёгкость сопровождения и возможность независимого тестирования каждого слоя.


1.8 История развития мобильных приложений для мониторинга здоровья

История мобильных приложений для мониторинга здоровья насчитывает немногим более пятнадцати лет и тесно связана с развитием смартфонов и носимых устройств. Можно выделить четыре этапа этого развития.

Первый этап (2008–2012 годы) связан с появлением первых массовых смартфонов (iPhone 3G в 2008 году, Android 1.0 в 2008 году) и открытием магазинов приложений App Store и Google Play. В этот период начали появляться простые приложения-трекеры: шагомеры, счётчики калорий, трекеры тренировок. Первые приложения использовали встроенные акселерометры смартфонов и не имели интеграции с носимыми устройствами. Типичными представителями этого этапа были Nike+ Running (2010 год) и Endomondo (2008 год).

Второй этап (2013–2017 годы) ознаменовался появлением фитнес-браслетов и «умных» часов. В 2013 году Samsung представила Galaxy Gear, в 2014 году Apple анонсировала Apple Watch, а в 2013 году на рынок вышел Xiaomi Mi Band. Эти устройства оснащались пульсометрами, акселерометрами и оптическими датчиками, что позволяло собирать медицинские данные непрерывно. В этот период появились платформы-агрегаторы: Apple Health (2014 год), Google Fit (2014 год), Samsung Health (2012 год). Основная архитектура приложений была основана на шаблоне MVC и XML-разметках Android.

Третий этап (2018–2022 годы) связан с развитием машинного обучения и облачных вычислений. Приложения стали анализировать данные не только непосредственно на устройстве, но и в облачных сервисах, предоставляя пользователям прогнозы, рекомендации по тренировкам и персонализированные программы питания. В этот период получили развитие специализированные медицинские приложения: MyTherapy (напоминания о приёме лекарств), One Drop (мониторинг диабета), Headspace и Calm (психологическое здоровье). В Android-разработке начали массово использоваться Kotlin (официальная поддержка с 2017 года), архитектурный шаблон MVVM и библиотеки Android Architecture Components.

Четвёртый этап (2023 год — настоящее время) характеризуется тремя ключевыми изменениями:
— унификация API работы с данными здоровья: Google выпустил Android Health Connect (2023 год), который стал единой точкой интеграции для всех приложений и носимых устройств на платформе Android;
— массовый переход на декларативные UI-фреймворки: Jetpack Compose для Android (стабильная версия — 2021 год) и SwiftUI для iOS (2019 год), что существенно ускорило разработку интерфейсов;
— рост внимания к конфиденциальности медицинских данных, вызванный скандалами с утечками данных (например, взлом MyFitnessPal в 2018 году, когда были украдены данные 150 миллионов пользователей). В ответ на это появились приложения, реализующие концепцию privacy-first, которая подразумевает локальное хранение данных и отсутствие сетевых запросов.

На текущем этапе ключевыми требованиями к новым приложениям mHealth являются: соответствие принципам Material Design 3 (Android) и Human Interface Guidelines (iOS), интеграция с Health Connect / HealthKit, шифрование персональных данных, возможность работы без сети и наличие функции экспорта данных для передачи медицинским специалистам. Разрабатываемое в рамках настоящей дипломной работы приложение HealtAPP удовлетворяет всем перечисленным требованиям и реализует современный подход к мобильной разработке.

В Республике Казахстан собственные нишевые решения в области mHealth находятся в стадии становления. На рынке присутствует несколько государственных и коммерческих приложений, связанных с системой электронного здравоохранения (eGov, Damumed, телемедицинские сервисы), однако приложения для личного самоконтроля здоровья с открытой кодовой базой практически отсутствуют. Это создаёт определённую нишу для разрабатываемого решения, в том числе с перспективой локализации на казахский язык.

2.4 Проектирование базы данных

Для локального хранения данных используется библиотека Room — абстракция над SQLite, официально поддерживаемая Google. Room предоставляет компиляционную проверку SQL-запросов, поддержку Kotlin Flow для реактивного получения данных и автоматическое управление миграциями.

База данных приложения состоит из шести таблиц:

1. `user_profile` — хранит профиль пользователя (id, name, heightCm, initialWeightKg, birthDateEpochDay, gender).
2. `weight_records` — хранит записи измерения веса (id, userId, weightKg, dateEpochMillis, note).
3. `blood_pressure` — хранит записи артериального давления (id, userId, systolic, diastolic, pulse, dateEpochMillis, note).
4. `steps` — хранит ежедневную агрегированную статистику шагов (id, userId, dateEpochDay, steps, caloriesKcal, activeMinutes, distanceMeters).
5. `state_of_health` — хранит оценки самочувствия (id, userId, level, bloodSugar, bodyTemperature, notes, dateEpochMillis).
6. `body_photos` — хранит метаданные зашифрованных фотографий (id, userId, encryptedPath, type, dateEpochMillis, notes).

[ВСТАВИТЬ РИСУНОК 2.3]
=== Описание: ER-диаграмма базы данных. Шесть прямоугольников-таблиц с
    перечислением полей и типов. Связи: user_profile (1) → weight_records,
    blood_pressure, steps, state_of_health, body_photos (каждая по userId).
    Подходит рисунок из DB Diagram (dbdiagram.io), draw.io или скриншот из

Для даты рождения используется кодирование в epoch day (количество дней от 01.01.1970), а для временных меток измерений — epoch milliseconds (миллисекунды UTC). Такой подход исключает необходимость конвертации часовых поясов на уровне базы данных.

2.5 Разработка доменного слоя (бизнес-логики)

Доменный слой реализован в виде 20 use case-классов, каждый из которых инкапсулирует одну бизнес-операцию. Use case-классы сгруппированы по подпакетам в соответствии с функциональной областью:

— bloodpressure: SaveBloodPressureUseCase, GetBloodPressureHistoryUseCase, GetBloodPressureStatsUseCase;
— dashboard: GetDashboardSummaryUseCase;
— health: SaveStateOfHealthUseCase, GetStateOfHealthHistoryUseCase, GetHealthTrendUseCase;
— photo: AddBodyPhotoUseCase, GetBodyPhotosUseCase, DeleteBodyPhotoUseCase, ComparePhotosUseCase;
— profile: GetUserProfileUseCase, SaveUserProfileUseCase, CalculateBmiUseCase;
— report: GenerateHealthReportDataUseCase, GenerateHealthReportPdfUseCase;
— steps: GetDailyStepSummaryUseCase, GetWeeklyStepStatsUseCase, SyncStepsFromHealthConnectUseCase;
— weight: SaveWeightRecordUseCase, GetWeightProgressUseCase.

Каждый use case получает необходимые репозитории через конструктор (dependency injection) и экспонирует функцию `operator fun invoke(...)`, что обеспечивает чистый вызывающий код:

    class SaveBloodPressureUseCase(
        private val repository: BloodPressureRepository
    ) {
        suspend operator fun invoke(bp: BloodPressure): Result<Unit> = runCatching {
            require(bp.systolic in 60..300) { "Систолическое давление вне диапазона" }
            require(bp.diastolic in 30..200) { "Диастолическое давление вне диапазона" }
            require(bp.pulse in 30..250) { "Пульс вне диапазона" }
            require(bp.systolic > bp.diastolic) { "Систолическое должно быть больше диастолического" }
            repository.save(bp)
        }
    }

Валидация входных данных выполняется на уровне use case, что исключает попадание некорректных значений в базу данных. Приняты следующие диапазоны допустимых значений:
— систолическое давление: 60–300 мм рт. ст.;
— диастолическое давление: 30–200 мм рт. ст.;
— пульс: 30–250 уд./мин;
— масса тела: 1–500 кг;
— уровень сахара в крови: 20–600 ммоль/л;
— температура тела: 30–45 °C.

│ Гипертония II стадии    │ 140–180              │ 90–120               │
│ Гипертонический криз    │ ≥ 180                │ ≥ 120                │
└─────────────────────────┴──────────────────────┴──────────────────────┘

Расчёт индекса массы тела (ИМТ) выполняется по формуле:

                         вес (кг)
            ИМТ  =  ─────────────────────                              (1)
                      рост² (м²)

где вес — текущий вес пользователя в килограммах; рост — рост пользователя в метрах.

Категории ИМТ:
— менее 18,5 — недостаточная масса;
— 18,5–24,9 — нормальная масса;
— 25,0–29,9 — избыточная масса;
— 30,0 и выше — ожирение.

=== Описание: Скриншот кода одного из use case-классов, например
    `SaveBloodPressureUseCase.kt` или `CalculateBmiUseCase.kt`. Можно также
    показать дерево проекта в Android Studio с раскрытым пакетом
    `domain/usecase/` и всеми 20 use-case-файлами. ===

Ниже приводится развёрнутое описание каждого из 20 use case-классов с указанием входных параметров, возвращаемого результата и бизнес-правил.

Пакет bloodpressure:

1. `SaveBloodPressureUseCase` — сохранение записи артериального давления. Принимает доменную модель `BloodPressure` с полями systolic, diastolic, pulse, dateEpochMillis, note. Выполняет валидацию значений (проверка диапазонов, проверку условия systolic > diastolic). Возвращает `Result<Unit>`. В случае успеха запись добавляется в таблицу `blood_pressure`, в случае ошибки возвращается исключение с описанием.

2. `GetBloodPressureHistoryUseCase` — получение истории измерений давления. Принимает идентификатор пользователя и опциональный диапазон дат. Возвращает `Flow<List<BloodPressure>>` — реактивный поток, автоматически обновляющийся при добавлении новых записей.

3. `GetBloodPressureStatsUseCase` — расчёт статистики давления за период. Принимает идентификатор пользователя и количество дней. Возвращает модель `BloodPressureStats`, содержащую средние значения систолического, диастолического давления и пульса, категорию классификации по ВОЗ, а также количество записей в выборке.

Пакет dashboard:

4. `GetDashboardSummaryUseCase` — формирование сводки для главного экрана. Агрегирует данные из всех репозиториев (шаги за сегодня, последнее измерение веса, последнее давление, последняя запись самочувствия) в единую модель `DashboardSummary`. Возвращает `Flow<DashboardSummary>`.

Пакет health:

5. `SaveStateOfHealthUseCase` — сохранение записи самочувствия. Принимает уровень (enum HealthLevel), опциональный уровень сахара, температуру и заметки. Выполняет валидацию: сахар 20–600 ммоль/л (при наличии), температура 30–45 °C (при наличии).

6. `GetStateOfHealthHistoryUseCase` — получение истории самочувствия с поддержкой фильтрации по диапазону дат.

7. `GetHealthTrendUseCase` — расчёт тренда самочувствия за 30 дней. Возвращает модель `HealthTrend` с распределением оценок по уровням (в процентах), средним уровнем сахара и средней температурой.

Пакет photo:

8. `AddBodyPhotoUseCase` — добавление новой фотографии. Принимает исходный URI изображения и тип (BODY или ANALYSIS). Внутри вызывает `PhotoStorage.encryptAndStore()`, который шифрует файл алгоритмом AES-256-GCM и сохраняет во внутреннее хранилище приложения. Возвращает идентификатор созданной записи.

9. `GetBodyPhotosUseCase` — получение списка фотографий пользователя с поддержкой фильтрации по типу.

10. `DeleteBodyPhotoUseCase` — удаление фотографии. Удаляет запись из базы данных и соответствующий зашифрованный файл из хранилища.

11. `ComparePhotosUseCase` — сравнение пар фотографий тела за период. Для каждой пары вычисляет перцептуальный хеш (16×16 пикселей, градации серого), рассчитывает расстояние Хэмминга между хешами и с учётом изменения веса за период между фотографиями выдаёт вердикт: «Заметный прогресс», «Небольшие изменения», «Визуальный шум» или «Слишком рано для сравнения».

Пакет profile:

12. `GetUserProfileUseCase` — получение профиля пользователя. Возвращает `Flow<UserProfile>`, автоматически обновляющийся при изменении профиля.

13. `SaveUserProfileUseCase` — сохранение/обновление профиля. Выполняет валидацию: рост 50–250 см, начальный вес 1–500 кг, дата рождения не в будущем.

14. `CalculateBmiUseCase` — расчёт индекса массы тела с классификацией. Принимает вес и рост, возвращает модель `BmiResult` с численным значением ИМТ и категорией (недостаточная масса, нормальная, избыточная, ожирение).

Пакет report:

15. `GenerateHealthReportDataUseCase` — сбор данных для отчёта. Принимает период в днях и агрегирует данные из всех репозиториев в модель `HealthReportData`. Используется как поставщик данных для генерации PDF.

16. `GenerateHealthReportPdfUseCase` — генерация PDF-отчёта. Вызывает `GenerateHealthReportDataUseCase` для получения данных, затем `PdfReportGenerator` для формирования документа. Возвращает путь к созданному PDF-файлу.

Пакет steps:

17. `GetDailyStepSummaryUseCase` — получение сводки шагов за день. Принимает дату, возвращает модель `DailyStepSummary` с количеством шагов, процентом выполнения цели 10 000 шагов, калориями и активными минутами.

18. `GetWeeklyStepStatsUseCase` — расчёт недельной статистики. Возвращает модель `WeeklyStepStats` со списком сводок за 7 дней, средним количеством шагов, максимумом и минимумом.

19. `SyncStepsFromHealthConnectUseCase` — синхронизация данных о шагах из Health Connect. Проверяет наличие Health Connect на устройстве, запрашивает разрешения, читает записи типа `StepsRecord` за последние 30 дней, агрегирует по датам и сохраняет в локальную базу данных.

Пакет weight:

20. `SaveWeightRecordUseCase` — сохранение записи веса. Принимает значение в килограммах и дату. Валидация: вес 1–500 кг, дата не в будущем. Возвращает `Result<Unit>`.

Дополнительный use case для работы с весом:

21. `GetWeightProgressUseCase` — расчёт прогресса изменения веса. Принимает идентификатор пользователя, возвращает модель `WeightProgress` с текущим весом, изменением от начального значения в килограммах и процентах, индикатором направления тренда (вверх/вниз/стабильно), количеством записей за период.

Таким образом, доменный слой содержит 21 use case-класс, покрывающий все функциональные возможности приложения. Разделение бизнес-логики на отдельные классы с единственной ответственностью (принцип SRP из SOLID) упрощает их независимое тестирование, поддержку и расширение. При необходимости добавления новой функциональности достаточно создать новый use case-класс, не затрагивая существующий код.


2.6 Обеспечение безопасности и конфиденциальности данных

Концепция privacy-first реализована на всех уровнях приложения:

1) Все данные (профиль, вес, давление, шаги, самочувствие, фото) хранятся исключительно в локальной базе данных Room и во внутреннем хранилище приложения. Сетевые запросы полностью отсутствуют.

2) Фотографии тела и анализов шифруются симметричным алгоритмом AES-256-GCM с использованием библиотеки Google Tink. Ключ шифрования генерируется при первом запуске и сохраняется в Android Keystore, обеспечивающем защиту от извлечения ключа даже при получении злоумышленником root-прав на устройстве.

3) Используется минимальный набор runtime-разрешений:
— ACTIVITY_RECOGNITION — для получения данных о шагах;
— READ_MEDIA_IMAGES — для чтения фотографий из галереи пользователя;
— CAMERA — для съёмки фотографий прогресса.

4) Для обмена PDF-отчётами используется механизм Android FileProvider, который позволяет безопасно предоставлять content://-URI другим приложениям без прямого доступа к файловой системе.

5) Параметр `android:allowBackup` установлен в значение `true` с использованием правил резервного копирования (`@xml/backup_rules`), исключающих из бэкапа зашифрованные фотографии и конфигурационные файлы с ключами шифрования.

2.7 Разработка пользовательского интерфейса

Пользовательский интерфейс реализован на основе архитектурного шаблона Single Activity Architecture: всё приложение представляет собой одну Activity (`MainActivity`), внутри которой выполняется композиция экранов и нижняя навигационная панель (`BottomNavigationBar`).

Корневой компонент `AppRoot` реализует навигацию между шестью основными вкладками: «Главная» (Dashboard), «Метрики» (с под-вкладками «Шаги», «Вес», «Давление»), «Здоровье», «Фото», «PDF», «Профиль». Итого приложение содержит восемь полнофункциональных экранов, каждому из которых соответствует свой ViewModel:

1. DashboardScreen + DashboardViewModel — сводка показателей.
2. StepsScreen + StepsViewModel — отслеживание шагов.
3. WeightScreen + WeightViewModel — отслеживание веса.
4. PressureScreen + PressureViewModel — отслеживание давления.
5. StateOfHealthScreen + StateOfHealthViewModel — дневник самочувствия.
6. PhotosScreen + PhotosViewModel — фото-дневник.
7. ReportScreen + ReportViewModel — генерация PDF-отчётов.
8. ProfileScreen + ProfileViewModel — редактирование профиля.

Дизайн-система построена на Material Design 3. Цветовая палитра использует акцентные цвета для визуального разделения категорий показателей:
— AccentSteps (#22C55E, зелёный) — активность и шаги;
— AccentMinutes (#3B82F6, синий) — время и сердечный ритм;
— AccentDistance (#F59E0B, оранжевый) — расстояние и энергия;
— AccentCalories (#EF4444, красный) — калории и давление;
— AccentNeutral (#6B7280, серый) — нейтральные метрики.

Общие UI-компоненты выделены в файл `ui/components/Components.kt` и включают:
— SectionCard — карточка с заголовком и закруглёнными углами;
— MetricRow — строка метрики с подписью и значением;
— ScreenTitle — унифицированный заголовок экрана;
— NumericField — поле ввода числа с валидацией.

Управление состоянием выполняется по шаблону Unidirectional Data Flow (UDF). Каждый ViewModel содержит `MutableStateFlow<UiState>`, который наблюдается экраном через `collectAsState()`. Пример:

    class WeightViewModel(
        private val getProgress: GetWeightProgressUseCase,
        private val saveWeight: SaveWeightRecordUseCase
    ) : ViewModel() {
        private val _state = MutableStateFlow(WeightUiState())
        val state: StateFlow<WeightUiState> = _state.asStateFlow()

        fun onInputChanged(value: String) { /* ... */ }
        fun onSave() { viewModelScope.launch { /* ... */ } }
    }

2.9 Тестирование приложения

Тестирование является неотъемлемой частью процесса разработки программного обеспечения и направлено на проверку соответствия приложения функциональным и нефункциональным требованиям. В рамках настоящей работы были проведены следующие виды тестирования: модульное (unit-тестирование), интеграционное и ручное функциональное.

Модульное тестирование выполнялось для слоя доменной логики (use case-классов) с использованием фреймворков JUnit 5 и MockK. Объектами тестирования являлись бизнес-правила валидации: диапазоны допустимых значений артериального давления, массы тела, уровня сахара в крови, температуры тела, а также логика классификации артериального давления по рекомендациям ВОЗ и расчёта индекса массы тела.

В ходе модульного тестирования были проверены следующие сценарии:
— сохранение корректных значений артериального давления (в пределах допустимых диапазонов) — ожидаемый результат: успешное сохранение;
— попытка сохранения значения систолического давления, равного 50 мм рт. ст. (ниже минимума) — ожидаемый результат: возврат исключения с сообщением о выходе за диапазон;
— попытка сохранения записи, в которой диастолическое давление превышает систолическое — ожидаемый результат: возврат исключения;
— корректность классификации давления: проверка пограничных значений 120/80, 130/80, 140/90, 180/120;
— корректность расчёта ИМТ: проверка на известных контрольных точках (рост 1,70 м, вес 70 кг — ожидается ИМТ 24,22);
— корректность расчёта прогресса веса: сравнение текущего веса с начальным, вычисление абсолютного и процентного изменения.

Интеграционное тестирование выполнялось для слоя работы с данными (Room). Использовался подход in-memory базы данных: для каждого теста создавался экземпляр `HealthDatabase` в оперативной памяти, выполнялись операции вставки и чтения, после чего база уничтожалась. Это позволило протестировать корректность SQL-запросов DAO-интерфейсов без использования физической базы данных.

Проверенные сценарии интеграционного тестирования:
— вставка записи через `BloodPressureDao.insert()` и последующее чтение через `getByUserId()` — проверка сохранности всех полей;
— фильтрация записей по диапазону дат через `getByDateRange()` — проверка корректности SQL-запроса с BETWEEN;
— подписка на `Flow<List<BloodPressureEntity>>` через `observeByUserId()` — проверка автоматического обновления при вставке новых записей;
— удаление записи и проверка отсутствия её в последующих выборках;
— обновление существующей записи через `update()` и проверка изменённых полей.

Ручное функциональное тестирование выполнялось на физических устройствах Android и в эмуляторе Android Studio. Для тестирования использовались следующие конфигурации:
— Samsung Galaxy A54 (Android 14, экран 6,4");
— Xiaomi Redmi Note 12 (Android 13, экран 6,67");
— эмулятор Pixel 7 Pro (Android 14, API 34);
— эмулятор Pixel 4a (Android 12, API 31) — для проверки совместимости с более старыми версиями;
— эмулятор с Android 8.0 (API 26) — минимальная поддерживаемая версия.

В рамках ручного тестирования проверялись пользовательские сценарии:
— первый запуск приложения и создание профиля пользователя;
— последовательное добавление измерений веса, давления, самочувствия;
— синхронизация шагов из Health Connect (при наличии приложения Health Connect на устройстве);
— добавление, просмотр и удаление фотографий тела;
— алгоритм сравнения фотографий и получение вердикта;
— генерация и отправка PDF-отчёта за 7 и 30 дней;
— переключение между вкладками и сохранение состояния экранов;
— поворот экрана (проверка сохранности состояния ViewModel);
— работа при включённом тёмном режиме системы.

3.2 Генерация PDF-отчётов и интеграция с Health Connect

Генерация PDF-отчётов реализована с использованием нативного Android API `PdfDocument`. Класс `PdfReportGenerator` создаёт документ формата A4 (595 × 842 точки) с использованием кастомных объектов `Paint` для форматирования текста: жирные заголовки, основной текст и мелкий приглушённый текст.

Процесс генерации отчёта включает следующие этапы:
1) `GenerateHealthReportDataUseCase` собирает все данные за указанный период из всех репозиториев;
2) `PdfReportGenerator` создаёт `PdfDocument`, рисует заголовки и разделы с данными;
3) готовый файл сохраняется во внутреннее хранилище приложения;
4) через `FileProvider` создаётся `content://`-URI для безопасного доступа;
5) открывается `Intent ACTION_SEND`, позволяющий пользователю выбрать приложение для отправки отчёта.

Интеграция с Android Health Connect

Android Health Connect — это единый API от Google для доступа к данным о здоровье и фитнесе, объединяющий данные от различных источников (Samsung Health, Google Fit, Fitbit и др.). Приложение использует Health Connect для синхронизации данных о шагах.

Класс `HealthConnectDataSourceImpl` реализует следующую логику:
1) проверка доступности Health Connect на устройстве через `HealthConnectClient.getSdkStatus()`;
2) создание экземпляра `HealthConnectClient` при первом обращении (lazy-инициализация);
3) чтение данных `StepsRecord` за указанный диапазон дат;
4) агрегация данных по датам (суммирование шагов за день);
5) преобразование в доменные модели `StepRecord`.

Use case `SyncStepsFromHealthConnectUseCase` вызывает этот источник данных, получает список записей о шагах и сохраняет их в локальную базу данных Room. Синхронизация выполняется за последние 30 дней.

[ВСТАВИТЬ РИСУНОК 3.15]
=== Описание: Диаграмма «Интеграция с Health Connect». Последовательность:
    [Android Sensors / Galaxy Watch / Mi Band] → [Android Health Connect] →
    [HealthConnectDataSourceImpl] → [SyncStepsFromHealthConnectUseCase] →
    [Room DB] → [ViewModel] → [StepsScreen]. Можно сделать в draw.io либо
    скриншот из Health Connect settings на телефоне. ===

В ходе выполнения данной дипломной работы была проделана значительная работа, начиная с анализа предметной области и рынка мобильных приложений для мониторинга здоровья и заканчивая реализацией и тестированием готового программного продукта. Полученный опыт стал неоценимым как с точки зрения приобретения теоретических знаний о современных технологиях мобильной разработки, так и в плане развития практических навыков проектирования и реализации сложных Android-приложений.

В результате работы было создано мобильное приложение HealtAPP для мониторинга показателей здоровья на платформе Android с использованием современных технологий Kotlin, Jetpack Compose, Room и Koin. Приложение предоставляет комплексный набор функций для отслеживания ключевых показателей здоровья: артериального давления, массы тела, физической активности, самочувствия и визуального прогресса тела.

При разработке приложения были решены следующие задачи:
— изучены существующие подходы к разработке мобильных приложений для мониторинга здоровья и проведён анализ рынка;
— проведён сравнительный анализ современных технологий для Android-разработки: Kotlin/Jetpack Compose, Flutter, React Native;
— исследован рынок существующих решений (Samsung Health, Google Fit, Apple Health и др.) и определены их сильные и слабые стороны;
— сформированы функциональные требования к приложению на основе проведённого анализа и медицинских стандартов;
— спроектирована трёхмодульная архитектура приложения на основе принципов Clean Architecture с разделением на слои domain, data и presentation;
— спроектирована схема локальной базы данных из шести таблиц и реализован слой доступа к данным на основе Room;
— реализовано 20 use case-классов с полной валидацией входных данных;
— реализовано мобильное приложение с 8 экранами и 8 ViewModels;
— обеспечено шифрование фотографий алгоритмом AES-256-GCM с использованием Google Tink и Android Keystore;
— реализована интеграция с Android Health Connect API для синхронизации данных о шагах;
— реализована генерация PDF-отчётов на базе нативного Android PdfDocument API.

Ключевой особенностью разработанного приложения является принцип privacy-first — все данные хранятся исключительно на устройстве пользователя, без передачи на внешние серверы. Это обеспечивает высокий уровень конфиденциальности медицинских данных и соответствует современным требованиям к защите персональной информации.

Приложение показало себя как удобный и функциональный инструмент для ежедневного мониторинга здоровья, адаптированный под потребности различных категорий пользователей. Использование технологий Kotlin и Jetpack Compose обеспечило высокую производительность и отзывчивость интерфейса, а применение архитектуры Clean Architecture — поддерживаемость и расширяемость кодовой базы.

Текущая архитектура намеренно ограничена клиентской частью: все бизнес-правила, алгоритм сравнения фотографий и генерация отчётов выполняются непосредственно на устройстве пользователя. Такое решение обосновано двумя причинами — конфиденциальностью медицинских данных и автономностью приложения, не зависящего от наличия сети. Однако разделение на модули domain и data, а также реализация всех источников данных через интерфейсы репозиториев, позволяют при необходимости безболезненно вынести часть функциональности на серверную сторону. В частности, более ресурсоёмкие алгоритмы анализа (сравнение фотографий с использованием нейронных сетей вместо перцептуального хеша, прогнозирование трендов показателей здоровья на основе машинного обучения) целесообразно перенести на бэкенд — для этого достаточно добавить новую реализацию соответствующего репозитория, обращающуюся к REST API, без изменения доменного слоя и пользовательского интерфейса.

Разработанное приложение может быть расширено в будущем: добавление авторизации через Firebase, синхронизация данных между устройствами, интеграция с носимыми устройствами (Wear OS), расширение алгоритмов анализа данных и добавление push-уведомлений с напоминаниями об измерениях.

            require(heightCm in 50..250)
            val heightM = heightCm / 100.0

            val category = when {

                bmi < 25.0 -> BmiCategory.NORMAL
                bmi < 30.0 -> BmiCategory.OVERWEIGHT
                else -> BmiCategory.OBESE
            }
            return BmiResult(value = bmi, category = category)
        }

Б.5 Класс PhotoStorage (модуль data)

Класс для шифрования и сохранения фотографий с использованием Google Tink:

    class PhotoStorage(private val context: Context) {
        private val aead: Aead by lazy {
            AndroidKeysetManager.Builder()
                .withSharedPref(context, "photo_keyset", "photo_prefs")
                .withKeyTemplate(AeadKeyTemplates.AES256_GCM)
                .withMasterKeyUri("android-keystore://photo_master_key")
                .build()
                .keysetHandle
                .getPrimitive(Aead::class.java)
        }

        suspend fun encryptAndStore(sourceUri: Uri): String {
            val plaintext = context.contentResolver.openInputStream(sourceUri)
                ?.use { it.readBytes() }
                ?: error("Не удалось прочитать файл")
            val ciphertext = aead.encrypt(plaintext, null)
            val file = File(context.filesDir, "photo_${System.currentTimeMillis()}.enc")
            file.writeBytes(ciphertext)
            return file.absolutePath
        }

        suspend fun decrypt(encryptedPath: String): ByteArray {
            val ciphertext = File(encryptedPath).readBytes()
            return aead.decrypt(ciphertext, null)
        }
    }

Ответ: Все данные будут удалены вместе с приложением. Перед удалением рекомендуется сгенерировать PDF-отчёт и сохранить его в безопасное место.

4. Пронумеровать страницы арабскими цифрами внизу справа (титульный лист
   считается стр. 1, но номер на нём не ставится — п.6.2 методички).
5. Добавить в конец приложения А, Б, В — ТЗ, листинги кода, скриншоты
   (если потребует руководитель).
6. Перед сдачей удалить этот раздел и заменить заглушки подписи научного
   руководителя в титульном листе.

Важно:
— Объём 50+ страниц достигается при правильном форматировании (TNR 14, 1.0,
   с рисунками). Если получается меньше — можно расширить разделы 1.1–1.3.
— Рисунок 2.1 (архитектура) и 2.3 (ER-диаграмма) рекомендуется рисовать в
   draw.io (бесплатно, экспорт в PNG).
